# desk

desk is the user's own vibe-coded workspace, TypeScript end to end in one pnpm workspace: a React app (`apps/web`: React, MobX, React Router, built with Vite) on a Node server (`apps/server`: Fastify, with the issues in SQLite, built into Node, inside the process; in Postgres through PGlite until 8 Nov). Every page address answers with the app, which reads its data from `/api/page/...` and gets each change pushed over `/api/sync`; the agents' JSON API (`/api/issues`...) is the one the desk skill documents. Node runs the server's `.ts` files as they are, with no build step. When desk starts, it installs packages if `pnpm-lock.yaml` changed (`apps/server/src/main.ts`) and builds the app if `apps/web` changed (`apps/server/src/web.ts`). Check types with `pnpm --filter server check`. The Python server it replaced (`desk/`, FastAPI) left the tree on 17 Oct and lives in git history. Its design doc is a file of the desk issue: `~/.local/share/desk/issues/desk/design.md`; the move to this stack is planned on the issue "desk on Linear's stack".

## desk's window

- **Code and build only the web version (`apps/web`).** The user uses desk in the browser and is abandoning the native window (`apps/native`, Rust, GPUI) and the Electron app (`apps/desktop`): "it's buggy, a lot of behaviors are gonna different from web app", "i'm gonna abandon rust and electron app. i'll just use the web version for now" (the user, 8 Nov). So a change touches `apps/web` and the server only. Change or build `apps/native` or `apps/desktop` only when the work explicitly names them, and never start either window. The bullets below say how they were set up; they are not a reason to keep them in step.
- desk's own window is a native app (`apps/native`: Rust, GPUI, as Zed is), since Electron's (`apps/desktop`) left on 8 Nov for its memory, about 100 MB against 400 ("build desk to linux native with lower ram using rust. not electron app anymore", the user, 8 Nov). It reads the same `/api/page/...` and `/api/sync` as the web app and copies its screens; the screens it does not have yet open in the browser at desk's address, each with a backlog issue named "Native window: ...".
- `desk-app.service` runs it all the time from `~/.cache/desk/native-target`, hidden at login, so that the Inbox's pop-ups come with it closed; closing it hides it on Hyprland's `special:desk` workspace, and the launcher's desk (`bin/desk-app`) brings it back ("hide", the user, 8 Nov). `apps/native/install.sh` puts the service and the launcher entry on the machine.
- Until the native window has every screen, Electron's app is back beside it, as only a window (`apps/desktop`, 8 Nov: "i still wanna use desk as electron app until it's completed. can i have two versions?", the user): the launcher's "desk (Electron)", class `desk-electron`, started on demand and quit when closed, with no service and no notifications, which the native window gives. `apps/desktop/install.sh` puts its launcher entry on the machine; its Electron runs from `~/.cache/desk/electron`, which `pnpm install` copies (`fuses.ts`).
- desk builds the window when it starts, as it builds the web app, whenever `apps/native` changed (`apps/server/src/native.ts`), but in the background, and starts it again on the new build only while it is hidden. Check it compiles with `cargo build` in `apps/native`, and test it against a test desk with `DESK_HOST=127.0.0.1:<port>` and `DESK_APP_ID=desk-native-test`: a Hyprland rule that places a test window matches that class, never `desk-native`, the real window's, which a test's rule once floated at the test's size (8 Nov).
- desk has no browser of its own since 8 Nov ("wanna remove chrome off desk ... just let the agent opens browser on /chrome", the user): a session opens pages in the agents' Chrome through the `chrome` skill, and nothing in desk draws, relays or keeps its tabs. A logged-out test uses `playwright-cli`.

## Working on desk's code

- Never edit the main checkout, `~/projects/desk`. The user's app runs from it on port 8790, on main and nothing else, and an edit there breaks the app mid-change (14 Oct: a half-done rename did exactly that). Nothing switches it to a branch for a test either: "desk is an important part of the workflow on the machine, we can't allow it to be interrupted while i'm working, with experiments on certain things" (the user, 2 Nov).
- Work on a feature branch in its own worktree, inside the checkout's `.claude/worktrees/`, which git ignores: `git -C ~/projects/desk worktree add .claude/worktrees/<name> -b feat/<name>`, then `pnpm install` inside it. Not `~/worktrees`, which the user cleared on 15 Oct: "desk will handle the dir". Never link `node_modules` (or anything) to the main checkout's: on 14 Oct git committed such a link for Python's `.venv`, and the merge replaced the real one with a link to itself.
- Test on a test desk, never on 8790 ("whichever changes are being made to it, it should be separated", the user, 2 Nov). Ask desk for one, naming your issue and your branch: `curl -s -X POST http://127.0.0.1:8790/api/issues/<slug>/test --json '{"branch": "feat/<name>"}'`. desk copies the user's data, the files and a dump of the database, into `~/.cache/desk/test-<port>`, starts a desk from your worktree on it as the unit `desk-test-<port>`, from 8791 up, and answers with its address (`apps/server/src/pool.ts`). Wait until its `/version` answers, then test the path you changed there and screenshot it.
  - It runs your worktree's files as they stand, but builds the app only from a commit that changed `apps/web` (`web.ts`): commit first, or run `pnpm build` in `apps/web` yourself.
  - Its log is `journalctl --user -u desk-test-<port>`. Ask again while you hold it, after a fix, and it starts again on your worktree's code, on the same copy.
  - It runs with `DESK_ENV=test` (`config.ts`), so nothing there reaches the user's things: no automations, no seat, a tmux server of its own, no relay, Approve runs no step, and each chat it resumes is a fork of the user's. Make whatever issues and chats the test needs: the copy goes with the desk.
- The test desks are a pool, in line ("my machine's resource likely won't be able to handle that. we need a pool, depends on the current machine state. likely just start at one for testing queue", the user, 2 Nov):
  - As many run at once as Settings' `test_slots` says (1 unless the user raises it, 4 at most), and one opens only while more than 4 GB of memory is free. Otherwise /test answers that you are queued, and why. End your turn then: the issue shows Waiting on a test desk, desk messages you once yours runs, and you carry on.
  - Hold it only while you test. Once you have your screenshots, give it back with `curl -s -X DELETE http://127.0.0.1:8790/api/issues/<slug>/test`, which stops it, deletes its copy and hands the slot to the next in line. desk takes it back on its own once your turn ends, two minutes after it told you at the earliest.
- A session with no issue runs a test desk by hand, from its worktree, on a copy of the files: `rsync -a --exclude .db ~/.local/share/desk/ /tmp/<name>/`, then `DESK_ENV=test DESK_DATA=/tmp/<name> PORT=8799 node apps/server/src/main.ts`, past the pool's ports. It reads the issues in from their files, with no chats. Stop it by its port, and delete the copy and `~/.cache/desk/sessions-8799.json` after.
- An issue's session, which desk starts in `~/projects/desk` and the user talks to in the issue's chat, works in a worktree as above, and holds its work there until the user approves it:
  - The user reviews the work in the chat, from each step's diagram, its diff in the chat's Changes and the screenshots from the test desk, which the session has given back by then. 8790 runs main until Approve lands the work, so the last report says what to try there once it has landed.
  - Its landing step, which it sends with its last step's report as its prompt says, is `~/projects/desk/bin/land feat/<name>`, with no `landed`: the script's last line says where it landed. On Approve desk runs it with no turn of the session's ("approve means just mark the issue done instead of another round of agent", the user, 22 Oct): the script rebases the branch onto main when main moved since it began, fast-forwards main to it and removes the worktree and the branch, and desk restarts on main. It checks nothing after a clean rebase ("usually they don't crash. and if they do, costing more token is valid", the user, 28 Oct), and it lands any repo's branch on main the same way.
  - When the step fails, because the branch does not rebase onto main cleanly or the worktree holds uncommitted changes, desk wakes the session with its output to land it itself. Rebase onto main in the worktree, resolving the conflicts, check the path again and land, with no second review ("after approve, and rebase, should merge immediately", the user, 15 Oct), by running `bin/land` again, or by hand, depending on where `~/projects/desk` stands:
    - On main, as desk keeps it: `git merge --ff-only feat/<name>` there, then `systemctl --user restart desk`.
    - Off main, switched by hand: leave it alone, fast-forward main from your worktree with `git fetch . feat/<name>:main` (git allows it while main is checked out nowhere, and only as a fast-forward), and tell the user 8790 does not run main.
    - Then remove the worktree and the branch, and tell desk it landed, with the call desk's message gives.
  - When the user throws the work away instead, give the test desk back with DELETE, which also takes you out of the line, and remove the worktree and the branch.
  - A session desk started before 15 Oct in a worktree it made (`claude -w`, branch `worktree-desk-<slug>`) cannot run git in `~/projects/desk`. It tests on a test desk with its branch, as above, and desk merges it on Approve.
- A session you run yourself, outside desk: when the path you changed works on a test desk, merge without asking ("when done testing, just merge", the user, 14 Oct), with `bin/land` as above.
- Sessions run in the session host (`apps/server/src/host.ts`, through the Agent SDK), a process of its own that desk starts in a systemd scope (`desk-host-<port>-*.scope`), so that desk's restarts leave running turns alone; its log is `~/.cache/desk/host-<port>.log`. The host tells desk each turn's start and end, each question waiting, and each process's end over a WebSocket to `/api/host`, and desk keeps that in the `sessions` table (`turns.ts`), which the Inbox and the sidebar read. Once new code lands, desk starts a host of it at once, beside the one still running (`hosted.ts`), each on its own socket, `desk-host-<port>-<version>.sock` in `$XDG_RUNTIME_DIR`: every new chat starts on the newest, a chat idle on an older one moves there on its next message, and an older one closes each chat idle for 5 minutes and quits once it holds none, while a turn running there finishes there ("i can't create new session for 10min. which is kinda suck", the user, 2 Nov). To end them all at once, `systemctl --user stop 'desk-host-8790-*'`, which ends every session's process; each resumes on its next message.
- The app on 8790 is desk.service: restart it with `systemctl --user restart desk`, never with `fuser -k` plus `nohup node`, which leaves a desk outside the service holding 8790 while desk.service crash-loops on "address already in use" (15 Oct: 429 restarts, and every running session killed).
- Stop any other server by its port (`fuser -k <port>/tcp`), not with `pkill -f`, whose pattern also matches the shell running it.
- A test desk is the unit `desk-test-<port>`: /test starts it and DELETE stops it, so leave its unit alone.
- Pace: test the path you changed on a test desk, screenshot it, give it back, move on.

## Data

- Issues live outside the repo, in `DESK_DATA` (default `~/.local/share/desk`, not a git repo since 9 Nov), so code work and merges never touch them.
- The database is the record of desk's state: SQLite's one file, `DESK_DATA/.db/desk.sqlite` (PGlite's folder beside it, `.db/pg`, is what desk read it from once on 8 Nov, kept as it was): issues, teams and projects, the Inbox's rows and what you read of them, the trash, pins, each session's model, settings and the test desks' line, `tests` (19 Oct: "you should find whatever represent state, should be in db"). No file holds a copy of an issue, team or project (until 8 Nov desk wrote each out as `issue.md`, `team.md`, `project.md`): an agent reads one with `GET /api/issues/<slug>` and writes through the API. An issue's folder holds only its real files, such as screenshots.
- pins.json, session-models.json and settings.json in `DESK_DATA`, and `desk-line` and `desk-trying` in the checkout's git dir, are what is left of the copies desk wrote out until 2 Nov, for branches from before 19 Oct: nothing reads or writes them. Never read desk's state from them.
- An issue's body is its one document, `## Context` and `## Plan` (19 Oct: "seemingly we don't need multiple files"), and every writer goes through the API: a session sends a section with `PUT /api/issues/<slug>/sections/<name>`, and the page's editor sends the document it started from, so a section it left as it was keeps what a session wrote meanwhile (`issues.ts`, "the document"). Only screenshots stay files, in the issue's folder. Its steps are rows of their own, one a step, in `steps` (`steps.ts`, since 8 Nov), each with what its session drew on it as Markdown; the issue holds its list in memory, which a save writes back row by row, only those that changed. An issue from before 4 Nov may also hold a `## Result`, which stays there, and an older one's `plan.md` and `result.md` went into the document on 8 Nov (`issues.ts`, leaveFiles). A session asks its questions in its chat.
- Every write to a table the app holds (issues, teams, projects, chats and the Inbox's rows so far) goes through `db.write` in `apps/server/src/db.ts`: one transaction, in which a trigger notes each changed row's key in `changed`, and the write takes those rows as they stand before it commits, for `/api/sync` to send the app. desk keeps no log of them since 8 Nov: an app back from a drop takes every row again. Never write those tables through `sql()`. A table the app should hold joins `HELD` there, which gives it its trigger.
